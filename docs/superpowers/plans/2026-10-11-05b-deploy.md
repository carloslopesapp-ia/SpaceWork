# SpaceWork — Plano 5B: deploy na Cloudflare (guia, feito com o dono)

> Este plano **não foi gerado por replay**: cada passo toca na conta da Cloudflare ou nas credenciais do dono, por isso fez-se à mão, com o dono, a 2026-10-10 e 2026-10-11, e este documento é o guia do que se fez, do que correu mal e de como se refaz. Os comandos que pedem credenciais correm no terminal do dono; **nunca se escrevem credenciais em ficheiros, commits ou conversas**.

**Resultado:** a aplicação corre em `https://spacework.carloslopesapp.workers.dev` (Worker `spacework`, D1 `spacework`, bucket R2 `spacework-files`, cron de hora a hora), e cada push para `main` publica sozinho (Workers Builds).

## O que se fez, por ordem

1. **Login do `wrangler`** (`npx wrangler login`). O primeiro login deixou um token sem permissões para a D1 (`Authentication error [code: 10000]` em `wrangler d1 list`): `npx wrangler logout` e `npx wrangler login` outra vez resolveu.
2. **D1:** criada com o nome `spacework` (`npx wrangler d1 create spacework`, ou no painel, em Storage & databases → D1). O `database_id` (um UUID, que não é segredo) foi para `wrangler.jsonc` (commit `6bb7e6c`). Com o placeholder `0000…` o deploy e os comandos `--remote` falham (`code: 10181` e `7404`).
3. **R2:** o bucket `spacework-files` foi criado pelo próprio primeiro `wrangler deploy` (o Wrangler cria os recursos que o `wrangler.jsonc` nomeia e que faltam).
4. **Migrações:** `npm run db:migrate:remote`. **Regra: uma migração nova aplica-se à D1 de produção antes do push que traz o código que a usa** (o deploy automático não corre migrações; o Worker novo daria 500 em tudo o que toca na base, e o `/api/health`, que só faz `SELECT 1`, não o mostra).
5. **O utilizador master:** `npm run seed:master -- --remote` (com `MASTER_EMAIL` e `MASTER_PASSWORD` no ambiente) falhou três vezes na prática: a senha pedida com `read` no terminal da app desktop apanhava o texto do comando seguinte. O caminho que resultou, sem passar a senha pelo terminal: **registar a conta pelo formulário do site e promovê-la a admin por SQL**:
   ```bash
   npx wrangler d1 execute DB --remote --command "UPDATE users SET role = 'admin', quota_bytes = 10737418240 WHERE email = 'o-email-do-master'"
   ```
6. **Git → Cloudflare (Workers Builds):** Worker de nome `spacework` (tem de coincidir com o `name` do `wrangler.jsonc`), repositório `carloslopesapp-ia/SpaceWork`, ramo `main`, comando de build `npm run build`, comando de deploy `npx wrangler deploy`, raiz `/`. As variáveis estão no `wrangler.jsonc`, não no painel.
7. **O registo da produção:** `REGISTRATION_OPEN = "approval"` (Plano 6): quem se regista fica por aprovar até o administrador aprovar em `/admin`.

## O que correu mal, e a causa

| Sintoma | Causa | O que resolveu |
|---|---|---|
| O build do Git falha no deploy com `D1 binding 'DB' references database '0000…' which was not found` | o `database_id` era o placeholder | pôr o ID verdadeiro e fazer push |
| `error code: 1042` e «There is nothing here yet» no endereço `workers.dev` | o `workers.dev` do Worker ficou «Desabilitado» (não se soube porquê) | ligá-lo em Domínios e rotas |
| «Tentar compilar novamente» continuou a falhar | reconstrói o **mesmo commit** do build falhado | fazer um push novo |
| «Email ou senha inválidos» com a senha certa | a senha guardada pelo `seed:master` não era a escrita (ver o passo 5) | o caminho do passo 5 |
| «Demasiadas tentativas» | 5 falhas por email em 15 minutos | `npx wrangler d1 execute DB --remote --command "DELETE FROM login_failures"` |
| O site «ficou igual» depois de um deploy | a página antiga em cache no browser | Cmd+Shift+R; confirmar também que o ficheiro `assets/index-*.js` servido mudou |

## Confirmado em produção (2026-10-11)

Pelo dono: o login, a criação e a aprovação de contas, o painel de administração, o deploy automático por push. Por mim, com pedidos de leitura ao endereço público:

- as páginas levam a CSP (`default-src 'self'; script-src 'self'; … object-src 'none'; base-uri 'none'`), `Referrer-Policy: same-origin`, `X-Content-Type-Options: nosniff` e `X-Frame-Options: SAMEORIGIN`: **o `public/_headers` é aplicado pelos assets do Worker**;
- a API leva `Cache-Control: no-store` e **não** leva CSP; `/api/health` responde `200 {"ok":true}`;
- `/api/auth/me` e `/api/admin/users` sem sessão dão `401`; `/s/<token>` cai no *fallback* da aplicação (`200`) e `/api/public/shares/<token inexistente>` dá `404` com a mensagem de «link indisponível»;
- o login e o registo (um PBKDF2 cada) correram sem o erro de limite de CPU do plano gratuito.

## Ainda por confirmar (precisam da conta da Cloudflare)

1. **O CPU da pior execução do PBKDF2** (login falhado, troca de senha, que faz dois): ver o percentil 99 do tempo de CPU em Métrica.
2. **O cron** (`0 * * * *`): em Configurações → Gatilhos deve aparecer; depois de uma hora certa, em Observability, uma linha `{"evento":"manutencao", …}`; e que uma execução com erro aparece como **falhada** no painel (o `scheduled` devolve a promessa de propósito). Medir o CPU da pior execução (4 páginas de 1000 objetos do R2 e 450 ids) e a contagem de subpedidos (32 no pior caso; o limite é 50).
3. **Os registos:** que mostram o relatório do cron e os erros e **não** mostram URLs (os registos de invocação estão desligados porque o token de um link de partilha vai no caminho).
4. O limite de 100 MB do corpo na Cloudflare (decimal ou binário, face a `MAX_UPLOAD_BYTES = 104857600`): um envio de 100 MB exatos.
5. Um teste de fumo de eliminar um ficheiro de vez (o objeto sai do R2).

## Sem plano (fica como possível melhoria)

- Uma regra de *rate limiting* da Cloudflare em `/api/auth/*` (o registo por aprovação já tira a pressão do registo aberto).
- Um teto ou prazo para os pedidos de registo por aprovar, e a verificação de que o email é de quem se regista.
- Alertas (por exemplo, de execuções falhadas do cron).
